二、生产环境 Kubernetes 架构设计
首先，我们看一下企业常见的 Kubernetes 高可用架构。
1. 推荐的生产环境架构
正式生产环境建议：
服务器		角色			数量
k8s-master1	Control Plane + etcd	1
k8s-master2	Control Plane + etcd	1
k8s-master3	Control Plane + etcd	1
k8s-worker1	Worker			1
k8s-worker2	Worker			1
k8s-worker3	Worker			1
LB1	HAProxy + Keepalived		1
LB2	HAProxy + Keepalived		1
总共8台服务器。

其中：
- 三个 Master：负责 Kubernetes 控制平面和 etcd。
- 三个 Worker：负责运行应用程序。
- 两个 LB：负责 API Server 负载均衡和 VIP 高可用。
注意：这是一个教学用的典型架构。实际生产环境还要考虑存储高可用、网络冗余、资源容量、故障域和备份位置。

2. 为什么建议三个 Master？
因为 etcd 使用 Raft 一致性协议，需要多数节点形成法定人数（Quorum）。
etcd 节点数	可以容忍的故障数
1		0
2		0
3		1
4		1
5		2
所以：3个 Master + 3个 etcd 成员，可以容忍一个 etcd 节点故障。
这里也纠正一个容易混淆的地方：两个 Master 在关闭其中一个后，另一个有时仍然能提供部分 Kubernetes 服务，
但两个 etcd 成员组成的集群已经失去多数派，不能正常进行新的数据写入。不能把这种现象当成真正的 etcd 高可用。

三、生产环境 API Server 高可用
在生产环境中，客户端不应该直接访问某一台 Master。
应该通过统一入口访问：
kubectl
   |
   v
192.168.79.100:6443
   |
   v
Keepalived + HAProxy
   |
   +--------------------+
   |                    |
   v                    v
Master1              Master2
   |
   v
Master3

这里的 192.168.79.100 是教学示例 VIP，不能直接照搬到你的 VMware 网络，必须确认地址没有冲突。
1. HAProxy 的作用
HAProxy 负责将 API Server 请求分发到可用的 Master。
默认 Kubernetes API Server 端口：6443
2. Keepalived 的作用
Keepalived 负责 VIP 漂移。

例如：
- LB1 正常：VIP 在 LB1。
- LB1 故障：VIP 漂移到 LB2。
- LB1 恢复：根据配置决定是否抢占 VIP。
3. HAProxy 配置示例
安装：dnf install -y haproxy
编辑配置：vi /etc/haproxy/haproxy.cfg
核心配置：
global
    log /dev/log local0
    maxconn 20000

defaults
    mode tcp
    timeout connect 10s
    timeout client  1m
    timeout server  1m

frontend k8s-api
    bind *:6443
    default_backend k8s-masters

backend k8s-masters
    balance roundrobin

    option tcp-check

    server master1 192.168.79.130:6443 check
    server master2 192.168.79.131:6443 check
    server master3 192.168.79.132:6443 check

启动：systemctl enable --now haproxy
查看状态：systemctl status haproxy
注意：这里的 Master IP 是示例地址，后面真正部署时要根据实际规划修改。

四、生产环境集群初始化自动化
生产环境不能每次部署 Kubernetes 都手动输入几十条命令。
通常会使用：
- Shell：编写自动化部署脚本。
- Ansible：批量管理 Linux 服务器。
- kubeadm：初始化 Kubernetes 集群。
- Helm：自动化部署 Kubernetes 应用。
- Terraform：自动化创建虚拟机和云资源。
1. 为什么要使用 Ansible？
假设企业有20台 Linux 服务器，需要统一执行：
systemctl disable --now firewalld
swapoff -a
modprobe overlay
modprobe br_netfilter
如果一台一台操作，效率很低。
使用 Ansible 可以一次性管理多台服务器。

2. 安装 Ansible
在管理节点安装：
dnf install -y epel-release
dnf install -y ansible-core
检查版本：ansible --version

3. 配置服务器清单
创建目录：
mkdir -p /opt/k8s-ansible
cd /opt/k8s-ansible
创建：vi hosts.ini
内容：
[k8s_masters]
master1 ansible_host=192.168.79.130
master2 ansible_host=192.168.79.131
master3 ansible_host=192.168.79.132

[k8s_workers]
node1 ansible_host=192.168.79.133
node2 ansible_host=192.168.79.134
node3 ansible_host=192.168.79.135

[k8s:children]
k8s_masters
k8s_workers

上面 IP 只是规划示例，与你现有的三台 VMware 虚拟机并不完全对应。

4. 配置 SSH 免密登录
在管理节点执行：ssh-keygen -t ed25519
分发公钥：ssh-copy-id root@192.168.79.130
其他服务器也分别配置。
测试：ansible all -i hosts.ini -m ping
如果返回：
SUCCESS => {
    "ping": "pong"
}
说明 Ansible 已经可以管理对应服务器。

5. 编写批量初始化 Playbook
创建：vi init-k8s.yml
内容：
---
- name: Kubernetes node initialization
  hosts: k8s
  become: true

  tasks:

    - name: Disable swap now
      command: swapoff -a

    - name: Disable swap permanently
      lineinfile:
        path: /etc/fstab
        regexp: '^\s*[^#].*\s+swap\s+'
        state: absent

    - name: Load kernel modules
      copy:
        dest: /etc/modules-load.d/k8s.conf
        content: |
          overlay
          br_netfilter

    - name: Load overlay
      modprobe:
        name: overlay
        state: present

    - name: Load br_netfilter
      modprobe:
        name: br_netfilter
        state: present

    - name: Configure IP forwarding
      sysctl:
        name: net.ipv4.ip_forward
        value: '1'
        state: present
        sysctl_file: /etc/sysctl.d/99-kubernetes.conf
        reload: true


执行：
ansible-playbook -i hosts.ini init-k8s.yml
这样就完成了所有节点的基础环境初始化。

注意：生产环境还需要统一检查 SELinux、时间同步、内核参数、containerd、镜像仓库和网络配置，
不能只执行这几个任务就认为节点已经满足安装条件。

五、Kubernetes 集群日常自动化巡检
生产环境最重要的工作之一，就是定期检查集群健康状态。
我们先编写一个简单的巡检脚本。

1. 创建巡检脚本
mkdir -p /opt/k8s-scripts
vi /opt/k8s-scripts/health-check.sh
输入：
#!/bin/bash

DATE=$(date '+%F %T')

echo "================================"
echo "Kubernetes Health Check"
echo "Time: $DATE"
echo "================================"

echo
echo "1. Node Status"

kubectl get nodes

echo
echo "2. Pod Status"

kubectl get pods -A

echo
echo "3. Failed Pods"

kubectl get pods -A --field-selector=status.phase=Failed

echo
echo "4. Cluster Components"

kubectl get pods -n kube-system

echo
echo "5. API Server Health"

kubectl get --raw='/readyz'

echo
echo "Health Check Finished"


赋予执行权限：chmod +x /opt/k8s-scripts/health-check.sh
执行：/opt/k8s-scripts/health-check.sh

2. 设置定时巡检
使用 Linux Crontab。
编辑：crontab -e
添加：
*/5 * * * * /opt/k8s-scripts/health-check.sh >> /var/log/k8s-health.log 2>&1
表示每5分钟执行一次。
查看日志：tail -f /var/log/k8s-health.log

3. 生产环境巡检应该检查哪些内容？
检查项目		检查命令
节点状态		kubectl get nodes
Pod 状态		kubectl get pods -A
Deployment	kubectl get deployments -A
PVC 状态		kubectl get pvc -A
Service		kubectl get svc -A
事件		kubectl get events -A
API 健康		kubectl get --raw='/readyz'
节点资源		kubectl top nodes
Pod 资源		kubectl top pods -A

注意：kubectl top 需要 Metrics Server 正常运行。
真正的生产巡检还应该增加异常判断、告警通知、日志轮转和巡检结果归档。
上面的脚本主要用于练习命令自动化，并不等于完整的告警系统。

六、生产环境节点维护与滚动升级
这是运维人员非常重要的一项技能。假设：
- Worker1 需要升级系统。
- Worker1 上面运行了多个业务 Pod。
- 不能直接关闭 Worker1。
应该怎么办？
答案是：先驱逐 Pod，再维护节点，最后恢复调度。
1. 查看节点
kubectl get nodes

2. 禁止新 Pod 调度
kubectl cordon k8s-node1
查看：kubectl get nodes
此时节点会显示：
SchedulingDisabled
注意：cordon 只是禁止新 Pod 调度，不会自动迁移已有 Pod。

3. 驱逐节点上的工作负载
kubectl drain k8s-node1 \
--ignore-daemonsets \
--delete-emptydir-data
参数说明：
参数	作用
--ignore-daemonsets	忽略 DaemonSet 管理的 Pod
--delete-emptydir-data	允许驱逐使用 emptyDir 的 Pod，并接受其中数据丢失
特别注意：
- emptyDir 中的数据会丢失。
- 使用本地存储的 Pod 可能无法迁移。
- PDB 可能阻止驱逐。
- 需要确认其他节点有足够资源接管业务。

4. 维护节点
例如：dnf update -y
如果升级了内核：reboot
这里生产环境不要盲目执行全部系统更新，应先在测试环境验证，并制定回滚方案。

5. 恢复节点调度
节点恢复正常后：kubectl uncordon k8s-node1
检查：kubectl get nodes

本节核心技能
这个操作流程要记住：
cordon
   |
   v
drain
   |
   v
维护节点
   |
   v
检查节点
   |
   v
uncordon


七、Kubernetes 集群版本升级
生产环境不能长期使用旧版本 Kubernetes。但升级也不能随意操作。
例如你现在的集群版本是：Kubernetes v1.37.2
升级前首先需要检查版本兼容性、官方支持的升级路径，以及 kubeadm、kubelet、kubectl 的版本关系。

1. 查看当前版本
kubectl version
查看节点：kubectl get nodes -o wide

2. 检查 kubeadm 升级计划
在 Master 节点执行：kubeadm upgrade plan
这个命令会检查当前集群状态以及可升级的目标版本。

3. 升级的大致流程
生产环境一般按照以下顺序：
备份 etcd
    |
    v
升级第一个 Master
    |
    v
升级其他 Master
    |
    v
逐个升级 Worker
    |
    v
检查所有节点
    |
    v
业务验收

对于 kubeadm 集群，Master 的升级还涉及：
1. 升级 kubeadm 软件包。
2. 执行 kubeadm upgrade apply（第一个控制平面）。
3. 其他控制平面执行 kubeadm upgrade node。
4. 逐个升级 kubelet 和 kubectl。
5. 重启 kubelet。
6. 检查节点和控制平面状态。
Worker 节点则使用 kubeadm upgrade node，并在维护窗口内升级 kubelet。
重要： Kubernetes 通常不支持跨多个 Minor 版本直接升级。例如不能随意从 v1.37 跳到 v1.39。
应按官方升级策略逐个 Minor 版本升级，并确保相关插件、CNI 和 CRI 兼容。
你现在使用的是 Kubernetes 1.37.2，后续实操我们应该以 1.37 系列的实际软件包仓库和官方升级说明为准，
不要直接套用网上 Kubernetes 1.28 的升级教程。

八、etcd 数据备份与灾难恢复
这是生产环境最重要的知识之一。为什么要备份 etcd？
因为 etcd 保存着 Kubernetes 集群的核心状态数据，例如：
- Pod 配置。
- Deployment 配置。
- Service 配置。
- ConfigMap。
- Secret。
- Namespace。
- RBAC。
- 节点信息。
如果 etcd 数据丢失，集群可能无法正常恢复。

1. 查看 etcd Pod
kubectl get pods -n kube-system | grep etcd
2. 检查 etcd 证书
ls -l /etc/kubernetes/pki/etcd/
通常可以看到：
ca.crt
ca.key
healthcheck-client.crt
healthcheck-client.key
peer.crt
peer.key
server.crt
server.key

3. 执行 etcd 备份
kubeadm 部署的集群通常可以在 Master 上使用 etcdctl。
先检查：etcdctl version
如果已安装，可以执行：
export ETCDCTL_API=3

etcdctl \
--endpoints=https://127.0.0.1:2379 \
--cacert=/etc/kubernetes/pki/etcd/ca.crt \
--cert=/etc/kubernetes/pki/etcd/server.crt \
--key=/etc/kubernetes/pki/etcd/server.key \
snapshot save /root/etcd-backup.db

注意：实际执行前要确认 etcd 监听地址、证书路径和 etcdctl 版本。
如果没有 etcdctl，需要使用匹配版本的 etcd 工具，不能直接假设系统已经安装。

4. 查看备份文件
ls -lh /root/etcd-backup.db
查看快照信息：etcdctl snapshot status /root/etcd-backup.db -w table

5. 生产环境备份策略
建议：
备份类型		建议频率
etcd 快照		每天至少一次
Kubernetes YAML	定期备份
业务数据库	根据业务 RPO 制定
PV 数据		根据存储方案制定
集群配置文件	每次变更后备份

特别提醒：
etcd 备份不等于业务数据备份。
如果你的 Java 项目使用 MySQL、Redis、MinIO 等外部存储，仍然需要单独备份这些数据。
备份文件也不能只放在 Master 本机上，应该异机或异地保存，并定期进行恢复演练。

6. etcd 灾难恢复
恢复时不能简单地把备份文件复制回原目录。
还需要考虑：
- etcd 成员关系。
- 集群 ID。
- 数据目录。
- 静态 Pod 配置。
- Kubernetes 控制平面证书。
- 多节点 etcd 的恢复协调。
生产环境恢复之前，必须先停止相关 etcd 实例，并根据实际拓扑制定恢复流程。
这部分我们后面会通过独立的故障恢复实验来操作，避免在现有集群上直接执行破坏性恢复命令。

九、Kubernetes 证书管理与自动续期
Kubernetes 使用 TLS 证书保护组件之间的通信。
例如：
- kubectl 与 API Server。
- API Server 与 kubelet。
- API Server 与 etcd。
- etcd 节点之间的通信。
证书过期可能导致集群组件无法正常通信。

1. 查看证书目录
ls -l /etc/kubernetes/pki/

2. 检查证书有效期
kubeadm certs check-expiration
可以查看：
- 证书名称。
- 证书到期时间。
- 剩余有效期。
- 是否可以通过 kubeadm 管理续期。

3. 续期所有 kubeadm 管理的证书
kubeadm certs renew all
检查：kubeadm certs check-expiration
注意：
1. 续期前先备份 /etc/kubernetes/pki。
2. 续期后需要根据组件类型重新加载证书，部分静态 Pod 需要重启。
3. 不要直接删除证书目录。
4. 不要将所有证书文件随意复制到其他 Master。
另外，kubeadm 管理的证书不等于所有集群证书。ServiceAccount 密钥、外部 CA 签发的证书等需要单独管理。

十、生产环境资源管理与应用可靠性
前面第10课学习过资源管理，这里从生产环境角度再强化一下。
1. Pod 必须配置资源限制
例如 Java 微服务：
apiVersion: v1
kind: Pod
metadata:
  name: java-demo
spec:
  containers:
    - name: java
      image: nginx:1.27
      resources:
        requests:
          cpu: "200m"
          memory: "256Mi"
        limits:
          cpu: "1000m"
          memory: "512Mi"

这里使用 nginx 镜像演示 Kubernetes 资源配置，后续 Java 项目会换成真正的 Java 镜像。
参数说明：
参数		作用
requests.cpu	调度所需 CPU
requests.memory	调度所需内存
limits.cpu	CPU 	使用上限
limits.memory	内存使用上限

2. 设置 Pod 分布策略
生产环境不要让所有业务副本都集中在同一台 Worker。
可以使用 Pod 反亲和性或拓扑分布约束。
例如：
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-ha
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-ha
  template:
    metadata:
      labels:
        app: web-ha
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: web-ha
      containers:
        - name: nginx
          image: nginx:1.27
作用：
尽可能将三个副本分布在不同节点上。
注意：如果可用节点不足，DoNotSchedule 会让部分 Pod 保持 Pending。这是为了保证分布约束，而不是调度故障。

3. 配置 PodDisruptionBudget
生产环境升级节点时，需要防止一次性驱逐太多副本。
创建：
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-ha-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web-ha
应用：
kubectl apply -f web-ha-pdb.yaml

查看：kubectl get pdb
含义：如果应用有三个健康副本，正常情况下至少保留两个可用副本。

十一、生产环境自动化运维体系
现在我们把前面的知识整合起来。
一个比较完整的企业级运维体系包括：
工具		主要职责
Ansible		Linux 和 Kubernetes 节点自动化管理
Shell		日常巡检、备份、维护脚本
Prometheus	指标采集
Grafana		监控可视化
Alertmanager	告警管理
Loki		日志收集
Argo CD		GitOps 持续部署
Jenkins		CI/CD 流水线
Helm		应用包管理
Velero		Kubernetes 资源及持久化卷备份（取决于存储插件）

这里需要区分：
- Prometheus 负责监控指标。
- Grafana 负责展示数据。
- Alertmanager 负责告警路由。
- Ansible 负责执行自动化运维任务。
- Argo CD 负责持续同步 Kubernetes 应用配置。
这些工具组合起来，才构成比较完整的自动化运维体系。

十二、本节课综合实战任务
接下来要在你的 Rocky Linux Kubernetes 实验环境中完成一次生产运维模拟。
先说明：你现在已经有一套三节点集群：
- k8s-master
- k8s-node1

十三、生产环境部署验收标准
一套 Kubernetes 生产环境不能只看 kubectl get nodes 是否显示 Ready。
还需要检查以下内容：
验收项目	合格标准
Master	控制平面正常
Worker	所有节点 Ready
etcd	集群健康，备份可用
网络	Pod 跨节点通信正常
Service	ClusterIP、NodePort 正常
Ingress	外部访问正常
存储	PVC 可以正常绑定和挂载
监控	Prometheus、Grafana 正常
日志	可以查询应用日志
安全	RBAC、NetworkPolicy 正常
自动化	Ansible、巡检脚本正常
备份	有异机备份和恢复演练
